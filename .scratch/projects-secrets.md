# Spec: `archon projects secrets`

Status: implemented on branch `projects-secrets`.

## Purpose and scope

Personal projects need local `.env` files that hold secrets and must not be
committed. The same secret, such as a GitHub token, is often needed in several
repositories. Keep every secret value in one local store and generate each
repository's `.env` from a committed template.

In scope:

- A new command group, `archon projects secrets`, with two commands:
  - `init` creates or completes the central store.
  - `sync` renders repository templates into `.env` files.
- A hard-coded list of allowed secret names in the CLI.

Out of scope:

- Adding `.env.template` files to repositories. The user does that separately
  in each repository.
- Encrypting the store or integrating a password manager.
- Running either command from `setup.sh`. Setup does not create, read, or
  modify the store.
- Repositories outside `~/projects/personal/<owner>/<repository>`.
- Templates below a repository root, such as `apps/web/.env.template`.

## Central store

Path: `${XDG_DATA_HOME:-~/.local/share}/archon/secrets/secrets.env`. Archon's
data directory holds one subdirectory each for the bootstrap clone (`repo`),
the skills checkout (`skills`), and secrets (`secrets`).

Do not put the store inside `archon/repo` or `archon/skills`, which are git
working trees. Do not use `~/.config/archon/` either: setup deletes and
recreates that directory on every run, because it is listed in
`data/home-replace-directories.txt`.

Format: one `NAME=value` entry per line. Blank lines and lines starting with `#`
are ignored. The value is everything after the first `=`, taken literally with
no quoting, escaping, or trimming. Values cannot span lines.

Allowed names are hard-coded in the CLI: `GITHUB_TOKEN` and `EODHD_API_TOKEN`.
The user adds names in code as needed.

## `archon projects secrets init`

- If the store does not exist, create its directory with mode `700` and the
  file with mode `600`. Write one `NAME=` line per allowed name, in list order.
  Print the created path.
- If the store exists and some allowed names have no entry, append `NAME=`
  lines for the missing names only. Leave existing lines and values unchanged.
  Print the path and the names that were appended.
- If the store exists and every allowed name has an entry, change nothing.
  Print that the file already exists and that there is nothing to do.
- Exit with `0` in all three cases.

## `archon projects secrets sync`

### Store checks

- If the store is missing, print its path, say to run
  `archon projects secrets init`, and exit with `1`.
- If the store is readable or writable by group or others, refuse to run,
  print the path and the required mode `600`, and exit with `1`.
- Warn about each store entry whose name is not in the allowed list, and ignore
  that entry.

### Rendering

Repositories are the ones `archon projects` already manages under
`~/projects/personal/<owner>/<repository>`. Only repositories with a
template at their root are processed. Repositories without one are not
reported.

Variants are rendered the same way: every root file named `.env.template` or
`.env.<variant>.template`, such as `.env.local.template`, renders to its name
without `.template`, such as `.env.local`. Each generated file is checked,
written, and reported separately. In the rules below, `.env` stands for the
generated file, and the header names its own template.

Rendering a template:

- Replace each `${NAME}` placeholder with the value from the store. `NAME`
  follows the shell variable name syntax.
- Leave any other `$` text unchanged. Do not use `envsubst`.
- Prepend this header line to the output:

  ```
  # Generated by `archon projects secrets sync`. Edit .env.template instead.
  ```

Skip a repository and do not write its `.env` when any of these applies:

- The template uses a name that is not in the allowed list.
- The template uses a name whose store value is empty or missing.
- `.env` is not ignored by git, as reported by
  `git -C <repo> check-ignore -q .env`. This also catches a tracked `.env`.

### Writing

- Compare the rendered content with the existing `.env`.
- When they differ or no `.env` exists, write it atomically with mode `600`:
  write a temporary file in the same directory, then rename it over `.env`.
- When they are identical, do not write the file.

Always overwrite `.env` when the content differs. The command does not detect
hand edits. The header line tells readers that the file is generated.

### Output and exit status

Print one line per processed repository:

```
created    mrzli/foo/.env
updated    mrzli/bar/.env
unchanged  mrzli/baz/.env
skipped    mrzli/qux/.env  (empty value: GITHUB_TOKEN)
```

- `created`: no `.env` existed.
- `updated`: `.env` existed with different content and was rewritten.
- `unchanged`: `.env` already matched the rendered output.
- `skipped`: the repository could not be rendered. The reason names the cause
  and the affected names.

A failure in one repository does not stop the others. If no repository has a
template, print a message saying so. Exit with `1` if any repository was
skipped or failed. Otherwise, exit with `0`.

## Agreed design

- **Commands:** nest the group under `projects` the way `projects libs` is
  nested. `run_projects` delegates `libs` to `Libraries.run_libraries`, and
  `secrets` follows the same pattern.
- **Help:** add help text for the group and both commands. List `secrets` in
  the global `archon projects` help. Use the existing `HELP` structure and
  argument handling: `-h`, `--help`, `help <command>`, and exit `2` for unknown
  commands or options.
- **Documentation:** add a `secrets` entry to
  `components/archon-cli/lib/archon/commands/projects/README.md`, which lists
  every projects command.
- **No new options:** neither command takes options beyond help. `--dry-run`
  is not in scope.
- **Dependencies:** use only Ruby's standard library and git, like the rest of
  the CLI.

## Acceptance and verification

Verify each item with automated tests in `components/archon-cli/tests/`. Use
an isolated home, an isolated `XDG_DATA_HOME`, and local git fixtures, following
`projects_test.rb`.

1. With no store, `init` creates the directory with mode `700` and the file
   with mode `600`, containing `GITHUB_TOKEN=`. It prints the path and exits
   with `0`.
2. When the store lacks an allowed name, `init` appends only that name and
   reports it. Existing values remain byte-for-byte unchanged.
3. When the store is complete, `init` leaves the file unchanged, including its
   modification time. It reports that there is nothing to do and exits with
   `0`.
4. With a missing store, `sync` exits with `1` and names `init`. With a store
   mode other than `600`, `sync` exits with `1` and writes nothing.
5. A template containing `${GITHUB_TOKEN}` and a literal `$OTHER` or `$5`
   renders with only the placeholder replaced, preceded by the header line.
6. The first run reports `created`. A second run with no changes reports
   `unchanged` and does not modify the file's modification time. After a store
   value or template changes, the run reports `updated`.
7. A written `.env` has mode `600`.
8. Each skip case reports `skipped` with its reason, leaves any existing `.env`
   untouched, and makes the command exit with `1`. The cases are an unknown
   name, an empty value, a `.env` that is not ignored, and a tracked `.env`.
   Other repositories in the same run are still processed.
9. A store entry with an unknown name produces a warning and does not affect
   the exit status.
10. Repositories without a template are not reported. With no templates
    anywhere, `sync` prints the no-templates message.
11. Help output covers the group and both commands. Unknown commands and
    options exit with `2`.
12. `bash components/archon-cli/tests/run.sh` passes.

Verification gap: the tests use fixtures. Running `archon projects secrets sync`
once against the real `~/projects/personal` is a manual check, and it only
changes gitignored `.env` files.

## Open questions

None block implementation.

- `sync` does not change the mode of an existing `.env` whose content already
  matches. Such a file keeps whatever mode it had, possibly `644`. Fixing modes
  on `unchanged` files would be a small follow-up if wanted.
